## Architecture

### One Worker, one origin

The whole app deploys as a single Cloudflare Worker described by the root `wrangler.jsonc`. `run_worker_first` is set to `/api/*`, so that is the only path that reaches Worker code; every other path is served from `client/dist` as a static asset, with `index.html` as the SPA fallback. No Pages project, no proxy hop.

`worker/src/index.ts` routes:

- `POST /api/oauth/discord/exchange` → `oauth-discord.ts`
- `/api/table/:tableId/*` → forwarded to the `GameTable` Durable Object via `env.GAME_TABLE.idFromName(tableId)`. The proxy rewrites the path and **overwrites** `?tableId=` from the URL segment, so a client-supplied table id can never make one table's DO touch another's rows. `TABLE_ID_PATTERN` bounds it.
- `scheduled` (hourly cron) → `pruneExpiredSessions` and `pruneOldMessages` (drops `messages` rows older than 30 days so the table cannot grow unbounded toward the account SQLite cap)

### Per-table state: Durable Object + D1

State is partitioned by `tableId`, one `GameTable` Durable Object per table.

- **`tableId` is `guildId-channelId`** (or just `channelId`), resolved in `client/src/main.ts`. It is deliberately **not** the Discord `instance_id`, which changes on every Activity launch and would give each session a fresh DO and blank sheets.
- **D1** (`ttrpg-activity-db`) is the durable store: `messages`, `characters`, `sessions_auth`, `facilitators`, `game_sessions`, `npcs`, `locations`. Schema is in `worker/migrations/`.
- **`GameTable`** loads `messages`, `characters`, the completed `game_sessions` history, and the `npcs` / `locations` reference rows from D1 on cold start into an in-memory `GameState`. Only the most recent `MESSAGE_WINDOW` (50) messages are held and broadcast, to keep the connect snapshot and each re-render small; older rows are fetched on demand through `GET /messages/history?before=<createdAt>` (read-only, no lock, no broadcast) and prepended client-side. The **die, the pending Junction, context aspects, the moves open to undo and the session are the only state the DO genuinely owns** — they live in DO storage (`KEY_TABLE_STATE`), not D1, because they would otherwise be lost on hibernation (~10s after a table goes quiet). `saveTableState` serialises that slice and skips the `put` when it is byte-identical to the last write, so mutations that leave it alone (a chat post, for instance) do not rewrite the blob.
- Because messages are read from D1 only on DO cold start, wiping the log means deleting the rows **and** cycling the DO (see `ROADMAP.md` "Flushing test messages").

### Realtime: broadcast is the source of truth

- Mutations — `POST /message`, `/messages/clear`, `/die/{step-up,step-down}`, `/junction/{roll,reroll,accept,reject}`, `/moves/{highlight,highlight-context,complicate,create,alter}`, `/moves/:id/undo`, `/context-aspects` and `/context-aspects/:id/{update,delete}`, `/session/{start,end,goal}`, `/characters/:slot/{update,fate,claim,release}`, `/{npcs,locations}` and `/{npcs,locations}/:id/{update,delete}` — return **`204` only**. They do not return a snapshot, on purpose: an HTTP body would race the WebSocket broadcast that already went out, and the two transports have no ordering. The move routes and the `claim`/`release` routes resolve the character sheet from the caller's Discord id (`characters.discord_user_id`), not a slot argument.
- **`RULES.md` is the source of truth for what the rules are** (the Junction loop, the five moves and their costs, context boons and banes); this section only records how the Worker implements them. `Copy/Terms.elm` (the in-app glossary) follows it, and the Guide carries its ladder odds table.
- **The die ladder (31.2b, ADR 0001)**: `gameState.die` is one of `LADDER` (`6, 8, 10, 12, 16, 20`, `rules/dice.ts`) and **returns to `BASE_DIE` (d10) whenever a Junction is accepted**. `classify(die, face)` reads 1–2 Critical Friction, 3–4 Friction, 5+ Flow, the top two faces Critical Flow. Between accepts the die changes only through an accepted Highlight or Use Context Boon (up), a context aspect the facilitator uses (its polarity's way), and the facilitator's `/die/{step-up,step-down}` (logged `d10 → d12`). A step past either end is refused (409) and spends nothing. A roll only ever *reads* the die.
- **The Junction loop (`rules/junction.ts`)**: `gameState.junction` is `{ rolledBy, die, face, outcome, rerolls, alteredSlots } | null`, persisted in `KEY_TABLE_STATE` and broadcast. `POST /junction/roll` is open to **any** authenticated player: it 409s if one is already pending, otherwise rolls the current die (`rollDie(die, deps.roll)`) and logs `Junction — <name> rolled: Flow — 7 on d10`. `/junction/reroll` (facilitator, free) rerolls on the Junction's own die. `/junction/accept` (facilitator) resets the die, adds a context boon for a Critical Flow or a context bane for a Critical Friction (credited to the roller), clears `junction`, closes every open move's undo, and logs the result with the die change. `/junction/reject` discards the roll and closes undo too; the die stays. Rolling closes every preparation move's undo, and **every move but Alter is refused while a roll is pending** (see Moves).
- **Moves act at once and are undone, not approved (31.3, ADR 0002, `rules/moves.ts`)**: `/moves/highlight` (`{ aspect }`, 1 boon, die up), `/moves/highlight-context` (`{ contextAspectId }`, anyone — no sheet needed — free, a boon steps the die up and a bane down, the aspect is consumed), `/moves/complicate` (`{ aspect }`, free, `COMPLICATE_BOONS` (2) and a blank context bane tagged `fromAspect`), `/moves/create` (`{ text }`, 1 boon, a context boon in the player's words or `Detail from <name>`) and `/moves/alter` (2 boons, rerolls the pending Junction on its own die, once per character per Junction via `junction.alteredSlots`). Highlight / Complicate / Create / Alter need a claimed sheet and a non-blank aspect where one is named (400); costs are checked once (400); a step past either end of the ladder is refused (409). **Every move but Alter is refused (409) once a Junction is rolled.** Each move records its `effects` as data on a `MoveRecord` in `gameState.moves` (`{ id, kind, actorId, actorName, slot, aspect, effects, messageId }`, DO storage only, broadcast); `messageId` is its log line. `POST /moves/:id/undo` (the facilitator, or the move's own actor; 403 otherwise, 404 once closed) applies the inverse of those effects, clamped at the ladder ends and at zero boons, so later moves survive; an Alter's roll is restored only if no later reroll replaced it. Rolling a Junction closes every undo window; accepting or rejecting closes the Alter ones; a sheet changing hands closes its slot's.
- **Context boons and banes**: `ContextAspect` is `{ id, kind, text, createdByName, createdAt, consumed, fromAspect }`. They come from an accepted Critical Flow or Critical Friction, a Create (a boon), a Complicate (a blank bane with `fromAspect`) or the facilitator (`POST /context-aspects`, any kind). They persist until the facilitator deletes them; spending one **marks it `consumed` rather than deleting it**, and a consumed one cannot be spent again. Anyone uses one through Highlight Context; undoing that clears the mark. Facilitator-only routes: `/context-aspects` (add), `/context-aspects/:id/update` (`{ text }`, silent) and `/delete`. `migrateTableState` drops the stone pool, a pending stone draw (no `die` → d10) and stored proposals, defaults `fromAspect` to `null`, and reads the older context-aspect names.
- **Sessions do nothing special (26.2)**: `rules/session.ts` records the goal on start and moves the session into `sessionHistory` on end (in memory; `persistDiff` closes the D1 row), and neither touches the die, open moves, context aspects or a pending Junction. `SessionState` is `{ id, goal, startedAt }` (a pre-31.2a blob's `startedAt` is backfilled from `game_sessions` on load); the goal is plain text, never judged, and can be rewritten with `POST /session/goal` (`facilitatorOnly`). `game_sessions.outcome` is not written; session history (`gameState.sessionHistory`) shows each past session's goal and dates. The message log is the persistent record of play.
- The resulting `GameState` is broadcast to every connected client over the table's WebSocket (`GET /api/table/:id/connect`, bearer token passed in `Sec-WebSocket-Protocol: bearer, <token>`).
- `GameTable` uses **hibernatable** WebSockets (`state.acceptWebSocket`). On connect it sends the current snapshot before any `await`, so a concurrent mutation's broadcast can only arrive after it.
- **The rules core (ADR 0003, roadmap 31.2a)**: `worker/src/rules/` exposes one pure `transition(table, command, deps)` — `Table` is `GameState` without `messages`, `Command` a union of every core mutation plus its `Actor`, `Deps` the injected `roll` / `now` / `newId` — returning `{ ok, next, log: LogEntry[], clearLog? }` or a refusal (`status`, `reason`). Role checks (`FACILITATOR_ONLY` in `rules/index.ts`) and ownership checks live in the core; `GameTable` only authenticates. The log is structured (`LogEvent`); `logText` in `rules/log.ts` is the one place it becomes stored text. Internal seams: `dice`, `junction`, `moves`, `session`, `sheets`, `entities`, `context`. `GameTable.fetch` matches `COMMAND_ROUTES` (path → `parse(match, body)` → `CommandBody`; parsing bounds and coerces but never refuses) and runs `apply`: `transition`, then `persistDiff(prev, next, messages)` (`persist.ts`, compares sheets / NPCs / locations / the running session and adds message rows) flushed by `toStatements` in **one `DB.batch`**, then install + `saveTableState` + broadcast with no `await` between. A no-op result (unchanged table, no log) acks without a broadcast.
- Every mutation runs through `withLock` — a promise chain that serializes DB write + in-memory update + broadcast. Durable Objects interleave concurrent requests at `await` points, so without this two mutations lost-update each other.
- Client side: the initial `GET /messages` seeds the board **only if** the socket snapshot has not already arrived (`GotGameState` checks `model.gameState`).

### Auth flow

1. Elm sends `Authorize` over the `toDiscord` port.
2. `client/src/DiscordBridge.ts` runs `discordSdk.commands.authorize` → auth code → `POST /api/oauth/discord/exchange`.
3. `worker/src/oauth-discord.ts` exchanges the code with Discord (no `redirect_uri` — Embedded App SDK codes are not issued against one), fetches `users/@me`, mints a random-UUID `sessionToken` into `sessions_auth` with an expiry, and returns `BackendAuthResult` (`sessionToken`, `accessToken`, `role`, …).
4. Bridge calls `discordSdk.commands.authenticate({ access_token })` to finish the Activity handshake, opens the game socket, and sends `BackendAuthResult` back over `fromDiscord`.
5. **Role**: `facilitator` if the Discord user id matches the `BOOTSTRAP_FACILITATOR_ID` var **or** is in the `facilitators` table, else `player` (`inferRole` in `oauth-discord.ts`, mirrored in `GameTable.getAuthFromToken`). Set `BOOTSTRAP_FACILITATOR_ID` in `wrangler.jsonc` (or `.dev.vars`) for a single known facilitator; seed the table for more.
6. Every `/api/table/*` route requires `Authorization: Bearer <sessionToken>` and checks `expires_at`. Facilitator-only routes (`die/{step-up,step-down}`, `junction/{reroll,accept,reject}`, `context-aspects` and `context-aspects/:id/{update,delete}`, `characters/:slot/fate`, `messages/clear`, `session/{start,end,goal}`, `{npcs,locations}` and `{npcs,locations}/:id/{update,delete}`) additionally 403 for anyone else, through `FACILITATOR_ONLY` in `rules/index.ts`. `moves/:id/undo` is open to the facilitator and to the move's own actor.

### Client module layout (Elm + TS interop)

Elm (`client/src/`), dependency direction `Types` ← everything, `Main` → `Effect`/`Api`/`Ports`/`View`/`Format`, `View` → `View/*` → `View/Helpers` → `Ui`:

- **`Main.elm`** — wiring only: `init` / `update` / `subscriptions` / `main`. `update : Msg -> Model -> ( Model, Effect )` is pure — it returns an `Effect` value, never a `Cmd` — and `main` runs `Effect.perform` on the result at the boundary.
- **`Effect.elm`** — an `Effect` type with one constructor per side effect the app performs (`GetGameState`, `PostMessage`, `PostJunctionRoll`, `PostHighlight` (carrying the `Aspect`), `PostUndo`, `ScrollLogToBottom`, `Authorize`, `Batch`, `None`, …), and `Effect.perform : Flags -> Effect -> Cmd Msg` translating each to an `Api` / `Ports` / `Task` call. `Post*` effects carry the `Auth` they need; `update` still decides whether the user is authorised. This is what lets `update` be asserted on in tests without mocking `Cmd`.
- **`Types.elm`** — domain types **plus `Model` and `Msg`**. They live here, not in `Main`, so `View` can import them without a cycle (`Main` imports `View`).
- **`Api.elm`** — every backend call. Endpoints are one line each over three private request helpers (`get` / `postEmpty` / `postJson`); commands take their result-message constructor as an argument, so this module has no dependency on `Types.Msg`.
- **`Api/Decode.elm`** — every decoder for what the Worker sends (the game state, a message, the auth result `Ports` forwards), and nothing else reads JSON. Its header maps each wire name to its Elm name (`kind` → `ContextAspect.polarity`, `fate` → the character's boons, …). A value the client cannot represent — a die off the ladder, an unknown outcome, polarity or move kind — fails the decode rather than defaulting.
- **`Ports.elm`** (`port module`) — the `toDiscord` / `fromDiscord` / `wsGameState` ports, `authorize`, and a typed `DiscordInbound` + `decodeInbound`. Ports declared here still surface on `app.ports`; the JS side does not care which module declares them.
- **Domain modules (31.4)** — `Die` (opaque; `ladder`, `base`, `sizes`, `fromSize`, `stepUp` / `stepDown` / `step : Direction -> Die -> Maybe Die`, `label`), `Outcome` (`CriticalFriction | Friction | Flow | CriticalFlow`), `Junction` (the pending roll: `die`, `face`, `outcome`, `rerolls`, `alteredSlots`), `ContextAspect` (`Polarity = Boon | Bane`, `fromAspect`), `MoveRecord` (`Kind = Highlight | HighlightContext | Complicate | Create | Alter`, its own module because those names also name `Msg` variants; `undoableBy`) and `Aspect` (`Archetype | Desire | Quest`, `toWire`). The view sees these, never a raw number or wire string; the Worker classifies every face.
- **`Action.elm`** — the mutations the UI guards against a double-click, as a type (`Action`) with a `Family` per group of results. `Model.inflight` is a `List Action`; `Main.guard` refuses an action already in flight, `MutationDone` clears a whole `Family`, and `Ui.press` greys a control whose action is pending. `inflight` rides on `ViewContext`. Its own module because `Effect` imports `View`.
- **`View.elm`** — the page shell only (roadmap 27, mockup 2a; moves placed by 31.5): `view` computes a `ViewContext` once, then composes a one-line status strip (`View.TopBar`) over three equal (`width fill`) columns split by `Ui.columnRule` hairlines: a **tool panel** on the left (a row of glyph tabs, `◆ Sheet` / `☺ Cast` / `? Guide`, showing one tool at a time via `Model.toolTab`), the context boons and banes and past sessions in the middle under a `Ui.divider` caption, scrolling, with the **Create** field pinned at the foot, and the event log with the composer pinned beneath it on the right. Every move is made where its subject is: Highlight / Complicate on the Sheet's aspects, Highlight Context on the context list, Create under it, Alter on the strip, undo on the move's log line. Only the context column and the log scroll; the tool panel's body keeps a `scrollArea` as an overflow fallback. Also `connectionNote`, `composer`, and the DOM ids `Main` focuses (`logDomId`, `aspectFieldId`, `contextAspectFieldId`).
- **`View/*.elm`** — one module per tool: `TopBar` (the status strip: the running goal — click it as facilitator to open the session start/end/goal controls — the die ladder `d6 … d20` whose current rung is the **roll button** while nothing is pending, the result beside it (`Flow · 7`), then a player's **Alter** or the facilitator's Reroll / Reject / Accept; the facilitator's `‹` `›` step the die either side of the ladder; and who you are), `Characters` (the Sheet: slot tabs and hairline label/value fields, boons as ☼ marks with the facilitator's Grant; on the viewer's own sheet each written aspect is a `Ui.splitButton` — left half Complicate, right half Highlight, each disabled with its reason as the tooltip — with a ✎ (`EditAspect`, `Model.aspectEditing`) that swaps in the field until it blurs), `Entities` (the Cast tab: NPCs and locations), `ContextAspects` (each aspect a Highlight Context button with its ☼ / ☽ mark, struck through once consumed; a Complicate's blank bane names its source until worded; the facilitator's ✎ (`EditContextAspect`, an entry in `contextAspectEdits`) and ×; `createField` — Create for a player, a free boon or bane with a ☼ / ☽ toggle for the facilitator), `Session` (past sessions), `Guide` (the `?` tab, `Copy.Terms` always expanded) and `Log` (an "undo" link on each move's line while it is open to the viewer — `MoveRecord.undoableBy`, matched by `messageId`). Each exposes `view : ViewContext -> <props record> -> GameState -> Element Msg` (a couple take no extra props; `Guide` takes nothing). `View/Helpers.elm` holds the `ViewContext` type (including `username`) and the cross-section helpers (`placeholder`, `inputAttrs` / `inlineInputAttrs`, `characterLabel`, the field ids, and the glossary-tooltip helpers `glossaryTitle` / `tip` / `tipAttrs` over `Ui.withTip` — `tip`/`withTip` shrink-wrap, so a full-width element takes `tipAttrs` directly instead, to leave its width alone).
- **`Ui.elm`** — the elm-ui design system: palette, `xs`…`xl` spacing scale, type sizes, and building blocks (`page`, `flat`, `toolTab`, `tab`, `primaryButton`, `ghostButton`, `linkButton`, `pencil`, `splitButton`, `boonMarks` / `baneMarks` (☼ / ☽, the bane in the danger tone), `oneLine`, `onEnter`, …), plus the `press` (in-flight gate) and `onlyWhen` list helpers. New UI goes through these, not raw `Element` styling. Aesthetic is deliberately spare and dense: no cards, just hairlines between regions, 11–13px type. `page` is a fixed-height shell (`{ top, columns }`, edge to edge); `scrollArea` is a tool's independently-scrolling body. It relies on `shrinkable` (`min-height: 0`) — CSS flex items default to `min-height: auto`, which refuses to shrink a flex-grow item below its content's natural size, so without it a panel (or a scrolling region nested inside one, like the Log's message list) just grows to fit its content instead of clipping and scrolling; `client/index.html` carries the matching `html, body, #root { height: 100% }` a `height fill` chain needs to reach a viewport to fill against — `#root` included, since a bare `<div>` does not inherit a percentage height from its parent. `shrinkableWidth` (`min-width: 0`) is the same fix across a row: the Sheet's fields put their input in such a slot rather than using `Input.labelLeft`, whose row gives elm-ui's multiline wrapper `flex-basis: auto` and so sizes it to its text on one line. `oneLine` is a nowrap-ellipsis text slot (a wrapping `paragraph` ignores `text-overflow`). `splitButton`'s washes and hover labels are CSS in `client/index.html` (`.split-*`, reached through `Ui.class`), since elm-ui's `mouseOver` cannot draw a gradient; on touch (`hover: none`) both halves keep a faint resting tint.
- **`Copy.elm`** / **`Copy/Terms.elm`** — `Copy.elm` is every player-facing string the view renders, as named constants grouped by card (small formatting functions where a value is spliced in), plus `aspectExamples : Aspect -> List String` (a curated subset of the repo-root `ASPECTS.md`, shown under "see examples" on each aspect field); structural labels that are not game vocabulary ("Name", "Notes") stay inline. `Copy/Terms.elm` is the glossary: `Term = { term, short, long }` and `terms` / `groupedTerms`, the `short` feeding the `title` tooltips and the `long` the `View.Guide` card, plus `ladderOdds` (the `RULES.md` odds table, copy rather than a calculation). `CopyTermsTest` fails if a term mentions a retired mechanic (stones, the pool, proposals, Add Detail, Alter Fate, …).
- **`Format.elm`** — pure helpers.

TypeScript (`client/src/`):

- **`main.ts`** — boots the Discord SDK, resolves `tableId`, `Elm.Main.init`, then wires the bridge and socket.
- **`DiscordBridge.ts`** — the Authorize flow and OAuth exchange. Imports `BackendAuthResult` from `worker/src/types.ts`, so the auth payload shape is shared across the client/worker boundary.
- **`GameSocket.ts`** — the reconnecting WebSocket feeding the `wsGameState` port. Gives up on close code `1008` (credentials rejected); exponential backoff otherwise.
- **`ports.ts`** — the one description of the Elm `app.ports` surface (`ElmPorts`, plus a `SocketPorts` pick for `GameSocket`), and the `Window.DISCORD_CLIENT_ID` / `Window.BACKEND_BASE_URL` global declarations. Imported by the three files above instead of each hand-copying the shape.

`client/scripts/build.mjs` calls `node_modules/elm/bin/elm` directly rather than the `.bin` shim, which breaks under pnpm.

## Conventions

- **Migrations are append-only.** Never edit a migration that may have been applied — add `worker/migrations/000N_name.sql`.
- **Do not edit `client/elm-stuff/`** (generated).
- Keep client and worker responsibilities separate. Keep ports narrow and typed.
- Worker code: explicit request validation and authorization at every route.
- After a change, run the narrowest check: `pnpm run build:client` after Elm, `pnpm run typecheck:worker` after Worker.
- `RULES.md` is the canonical, current statement of the game rules. Any change to a game rule updates it in the same branch, and `client/src/Copy/Terms.elm` (the in-app glossary) follows it.
- `CONTEXT.md` is the glossary: the canonical name for every game concept, with retired names under _Avoid_. Name code, copy and log lines after it. Decisions that are hard to reverse and surprising without context get an ADR in `docs/adr/`.
- `ROADMAP.md` is forward-looking; `CHANGELOG.md` is the record of what shipped — add a bullet to its `[Unreleased]` section for any notable change.
